## 2026-11-09: self-check 0.2.5, self-exit 0.1.7, self-restart 0.4.3, self-switch 0.4.3, self-wake 0.3.4: a window keeps its later restarts in the same window

- **The problem.** self-restart and self-switch resume in the same tab only under the claude wrapper (`tools/claude-wrapper/claude-wrapper.ps1`, a `claude` function in the person's profile). A move from a session that wasn't typed under it opens a new window, and that window started `claude.exe` directly from Windows PowerShell 5.1, with `CLAUDE_PANE_TOKEN` dropped: so every later restart of that session opened yet another window. Seen live: 6 of 9 sessions on one machine were such windows. And a machine with no wrapper installed, or no PowerShell 7, never got the same tab at all.
- **A window runs claude through the claude wrapper, with nothing to install.** The shared machine code carries the wrapper byte for byte (`WRAPPER_SCRIPT_TEXT`, pinned by `WRAPPER_SCRIPT_SHA256`). Every launch that may open a window puts it beside `claude-launch.ps1`, at its own hash's name (`wrapperScriptPath`: `%LOCALAPPDATA%\claude-self-tools\claude-wrapper-<sha8>.ps1`), the way the launcher is put there (written whole under another name, checked, moved over), and is never refused on it. The window runs `claude-launch.ps1 ... -Wrapper`.
- **`claude-launch.ps1` version 4: `-Wrapper`.** After it finds `claude.exe` and before its last look, it reads that copy's bytes once, checks their SHA-256 against `$WrapperSha256` (the same pin, inside its own pinned text: a change to the wrapper is a change to the launcher), and defines the wrapper's `claude` function from those same bytes. Execution policy is never asked (a script block made from text, never the file by its path), so it works under any policy, `Restricted` too, and with Windows PowerShell 5.1 alone. Then, after the last look and the launch environment (unchanged: `NO_COLOR` and the markers cleared, `PSExecutionPolicyPreference` and the inherited `CLAUDE_PANE_TOKEN` dropped, the two settings set), it calls that `claude` (the function it made, never the name) with the same arguments, in its own process: claude gets a fresh token and a pane file (version 3, `"hosted": true`) naming the window's PowerShell, its own parent, so the session's next restart or switch takes the `pane` transport and comes back in that window. A copy missing, changed or unreadable is said in one line in the window (`claude-launch: the claude wrapper is not used: <why>. Claude starts directly, so a restart from this session opens in a new window or tab.`), and claude starts directly, as before. A slot runner never passes `-Wrapper` (it has its own loop); by hand it is optional. The person's own `claude-wrapper.ps1` is never read by a launch.
- **The window's interpreter.** PowerShell 7 when `pwsh.exe` is at its standard path (`PowerShell\7\pwsh.exe` under the Program Files folder as Windows names it, never the `ProgramFiles` variable; held to `PWSH_PATH` as Windows PowerShell is held to its known path, there, and of version 7 or later), else Windows PowerShell 5.1 by its known path, as before; chosen by the launch script right before `Start-Process`. The window script and `claude-launch.ps1` run in either, and the wrapper's pane file names whichever it is.
- **Compatibility.** The window's copy and a profile's copy are the same file: both write the pane file of version 3 (the window's adds `"hosted": true`, which the plugins' reader takes and older ones ignore) and read the ticket of version 1 the plugins write. An older profile copy (pane file version 2) is taken as before, for a move that reads one config folder.
- **`tools/claude-wrapper/claude-wrapper.ps1`**: its header says how a window uses it. Hosted by `claude-launch.ps1` (`$ClaudeWrapperHosted` in the calling script's scope), it has no cap of 10 moves, its pane file says `"hosted": true`, and it leaves the calling script the conversation it resumed last and a ticket it didn't use (`$ClaudeWrapperLast`, `$ClaudeWrapperUnused`: two harmless variables of a profile's session). Typed at a prompt, it behaves as before.
- **Shared code**: `shared/hooks/machine.ts`: `WRAPPER_SCRIPT_TEXT`, `WRAPPER_SCRIPT_SHA256`, `wrapperScriptPath`, `PWSH_PATH`, `pwshPath`; the window's `-Wrapper` and its interpreter; the wrapper's copy put in place; `WRAPPER_UNUSED_EXIT`; `Pane.hosted`; `LAUNCH_SCRIPT_TEXT`, `LAUNCH_SCRIPT_SHA256` and `LAUNCH_SCRIPT_VERSION` (4) for the new launcher; `SLOT_SCRIPT_SHA256` and `LAYOUT_SCRIPT_SHA256` for the slot runner's and the layout script's module path (below). `scripts/embed-launch.mjs` pins the wrapper first. `shared/hooks/machine.ts` is now SHA-256 `d64e93ea96932466d21cde1c4015ee47e1e1250fc8a231810f09b46cb576477b`; the coordinator (agent-coordinator-3000), which vendors this file with these pins, picks it up in its re-vendor (its issue #98).
- **Tests.** `scripts/claude-launch.test.mjs`: the copy equal to the tools file and both pins; the wrapper's top level only its function; the load's order (read once, hashed, compared, defined, before the last look) and no file dot-sourced; then for real in Windows PowerShell 5.1 and PowerShell 7 against the stub: `-Resume`, `-Start` and `-Lane` with `-Wrapper` (claude right under the shell, a fresh token, the pane file naming it), no copy, a changed copy and the person's copy alone (direct, said), and a Restricted policy for the process alone; planted: no wrapper use, the fallback silent, the hash check skipped, the token dropped, the copy dot-sourced by its path. `scripts/launch-live.test.mjs`: a window's launch end to end, its `Start-Process` recorded (never a window), then its very command run hidden: PowerShell 7 at its path, or 5.1 with none there under a Restricted policy; claude under the window through the copy the launch put there; the probe run under that claude giving `pane` to `pickLaunchTransport` and `pickTransport`; the ticket the plugins write taken in the same window; and the copy gone or changed. `scripts/claude-wrapper.test.mjs`: a resume under a Restricted policy. The stub claude.exe logs its parent and the tab's token; `stub.mjs`'s fence refuses any PATH folder holding a claude program, and the tests that passed the whole environment (`former-names`, `left-record`) take such folders off it.

## 2026-11-09: self-hierarchy 0.1.0: a skill for running sessions as a hierarchy

- **New: self-hierarchy 0.1.0**, the marketplace's first plugin that is a skill and not a mod. Its skill, `session-hierarchy` (`skills/session-hierarchy/SKILL.md`, with `reference.md` beside it), says how several Claude Code sessions on one machine run together: one owner, a coordinator session, a merger session and lane sessions, with builder and reviewer subagents.
  - **The roles**: the coordinator owns priorities, routing, spawning, retiring and restarting sessions, plugin rollouts, broadcasts, conflicts between areas and the scope of rules; the merger owns push asks, independent reviews, merge calls on findings, the merge queue and promotion prep, and never accepts its own protected heads (the coordinator does); lanes own areas; subagents do the work.
  - **Who answers what**, work outside a session's area, the review loop, the owner's decisions, messaging between sessions, heavy work, waiting, and pause and resume.
  - **The self tools in a hierarchy**: what compacting, restarting, clearing, switching, exiting, waking, reloading and `tools_check` each cost and when to use which; what an in-process `/clear` or `/resume` does to plugin state; same-tab restarts, and launching a session through the claude wrapper with Claude Code's session markers cleared and `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1` set; names, Remote Control, and an optional colour per role with `/color`.
  - Its description loads it when a session is told it is the coordinator, the merger or a lane, or asks how to run or join such a group; never for ordinary work in a single session.
  - No hooks, no tools, no settings, no update check and no network request.
- **Shared code goes to mods only.** `scripts/sync-shared.mjs` copies a shared file without a `Copies:` line into every mod (each plugin with `hooks/hooks.json`, `mods()`), no longer into every plugin, so a plugin of skills alone carries no update check it could never run. `scripts/shared-copies.test.mjs` holds the update check to every mod, holds self-hierarchy to no shared code, and its fixture adds a plugin of skills alone whose planted copy reads as stale. A plugin with a `hooks/` folder but no `hooks/hooks.json` is an error in `sync-shared.mjs` and `test-all.mjs`, naming the plugin, and never a plugin of skills alone: a hooks.json lost by mistake would otherwise cost a mod its copies and its tests without a word. Nothing is written, removed or run then. No mod's copies change.
- **`scripts/test-all.mjs` runs `claude plugin test` for mods only.** `claude plugin test` refuses a plugin with no hooks module ("no hooks module to load"), so a plugin of skills alone is validated (`--strict`) and not tested.
- **The root README and the marketplace** list self-hierarchy, its install lines, and a line for `CLAUDE.md`.

## 2026-11-09: self-check 0.2.4, self-exit 0.1.6, self-restart 0.4.2, self-switch 0.4.2, self-wake 0.3.3: a return trip in place reads formerNames as a conversation held earlier (#31)

- **The bug (#31, High, recycling).** A return trip in place, to the conversation the same process held before, was always refused. Claude Code's session registry keeps the conversation a process left in place in `formerNames[].sessionId`, and the shared machine code took a conversation named anywhere in a running process's registry file outside `sessionId` as unknown: "unknown: the registry file of running claude.exe <pid> names it outside its sessionId". Seen live on 2026-11-09 with coordinator 0.9.3: the left record had already waived L3 and L5, the refusal came from the registry check alone, and the process naming the target was the switching process itself.
- **The rule now** (`shared/hooks/machine.ts`, in each plugin that carries it; nothing else changes in these plugins). A process's `formerNames[].sessionId` is a conversation it held earlier, not one it holds now. It counts as settled only when that process is the switching process itself (`self`: its pid and start, the probe seeing it running with that start and its registry file current) and the probe read that process's left record of that conversation: one record, of its shape (version 1), its MAC matched, naming that conversation, by that pid and start. Any other process naming it in `formerNames`, this one's without that record, or the conversation named anywhere else in the file, is unknown as before. L1 to L6 and the left record's waiver are unchanged.
  - **The probe** reports, per registry file, the asked-about ids that are a `formerNames` entry's `sessionId` exactly (`former`) apart from those named anywhere else (`mentions`), with one PowerShell function, `Get-Mentions`. A `formerNames` that isn't a list, an entry that isn't an object, an entry's other keys and their names, and a `sessionId` of another case or text are all searched as text, so they stay in `mentions`. `parseProbe` checks `former` as it checks `mentions`.
  - **`liveness`**, given `self` and `left`, says why in its evidence: "held earlier, not now: the registry file of claude.exe <pid>, this process, names it only in formerNames, and this process's left record says it left it".
  - **The in-place last look** (`claimCheckScript`) takes `self` too. With it, the script reads this process's left record of the conversation itself (its MAC checked inside the script, as the probe reads it), and its re-check is `RECHECK_SELF`: RECHECK plus one line, right before the refusal of a conversation named outside its sessionId, that lifts that refusal only for this process's own current registry file (its pid, and its start as the file and the process table both say) naming the conversation only as a `formerNames` entry's `sessionId`, with that record. Without `self`, the script is as it was. RECHECK, and its copies in the window, the slot runner, the claude wrapper and claude-launch.ps1, are unchanged (none of them runs beside the process it checks), so `LAUNCH_SCRIPT_SHA256` and `SLOT_SCRIPT_SHA256` stay.
  - **A caller passes `self`.** Neither self-switch's own switch nor the coordinator's go passes it yet, so a return trip is refused as before until one does. The coordinator's re-vendor (PR C) passes this process (the probe's `session`) to `liveness` and to `claimCheckScript`.
- **`shared/hooks/machine.ts`**, SHA-256 `5b7024434867e915c83fc048e887b0511dcdcdff3f29d8109375b3fb40da684c`; the coordinator vendors it again (PR C).
- **Tests.** self-switch `tests/return-trip.test.ts`, on fixture probes: the return trip passes; the same `formerNames` entry with no left record, with a record by another pid or another start, of another conversation, of another shape, with a MAC that doesn't match, two records, records that can't be read, or a caller that takes none; no `self`, or a `self` of another start; the id named elsewhere in the file too; a stale file of the same pid; and another process naming it in `formerNames` all stay unknown, and another process holding it in `sessionId` stays live (L1). Each of these is paired with the return trip that passes, so each fails without the fix. Also `former`'s parsing, and the text of `RECHECK_SELF` and of `claimCheckScript` with and without `self`. `tests/machine.test.ts` reads the probe's new lines. `scripts/former-names.test.mjs` runs the probe and the in-place last look for real on Windows, against two stub claude.exe and a left key made at run time.

## 2026-11-08: self-restart 0.4.1, self-switch 0.4.1, self-wake 0.3.2, self-remote-control 0.4.1, self-reload 0.1.3: plugin state emptied at an in-process /clear or /resume (#24), and the resume claim's key (#23)

- **The bug (#24).** Claude Code empties every plugin's `$.state` when a session ends inside the process: at a `/clear` or a `/resume`, typed, run by `clear_after_turn`, or by an in-place switch. The module goes on running, and no `session.start` follows, so a value written only there stays gone. **The rule now, for every key that must outlive a move:** the module keeps its own copy, and `$.state` only the copy that outlives a reload; the copy goes back with a plain set at each main-loop classic SessionStart of a clear or a resume, and again at the first read that finds the key empty (the wipe may land after that SessionStart). Each put-back is safe to repeat, and no compare-and-set uses a version held from before a move.
- **self-restart 0.4.1: the start folder** (High). Kept in the module from the first `session.start`, read first, and put back as above. At the call and right before the launch, the folder is checked against the conversation's transcript: the `transcript_path` a classic SessionStart named sits in its project folder, or `<config>\projects\<project>\<id>.jsonl` exists. A folder that fails (a reload after the wipe set it from a worktree) gives way to `$.session.root()`, then `$.session.cwd()`, each only when it passes. With none, the call is refused, saying why and what to tell the person (see the review below). **Every refusal of what the launch needs now comes at the call** (off Windows, an id `claude --resume` doesn't take, the Windows folder, the config folder, the start folder), never "Queued" and refused after the turn; the call's result no longer says "On anything but Windows nothing runs, and you are told on your next turn."
- **self-switch 0.4.1: the start folder** (Low). The module's copy goes back to `$.state` at each clear's or resume's SessionStart, and whenever the heartbeat finds it empty. A `session.start` that finds no start folder kept anywhere holds its own folder provisional, and takes it only once this process's startup SessionStart names the conversation or the folder holds the conversation's transcript (no prompt is no proof: a `/clear`'s conversation has none). Meanwhile the start folder is unknown, the log says why once, a switch refuses, and the heartbeat goes on with the last beat's folder carried forward.
- **self-wake 0.3.2: the armed wake-up** (Medium). The module keeps the whole wake-up, put back as above; `fire()` goes by it when `$.state` reads empty, so the wake-up is sent, once. `wake_after` and `cancel_wake` see it after a wipe too. A timer that sends nothing leaves the status line pinned to a wake-up still armed, else clears it ("wake-up pending" no longer stays). What a move makes of it is in the review below.
- **self-remote-control 0.4.1: the login record and the servers seen** (Medium). A module mirror of each, set at every write; a read that finds one empty while its mirror is set writes the mirror back and goes by it, and both go back at each clear's or resume's SessionStart. A login change after a move is no longer taken as the baseline, and one being handled then is no longer dropped. The last turn and the resume's record are still forgotten at a move.
- **self-remote-control 0.4.1: the resume claim's key (#23).** A turn now keeps the conversation it ran in (`session`): the one the last main-loop SessionStart of a startup, a resume or a clear named, while `$.session.id()` lags that move (up to 15 s), else `$.session.id()`. The claim is `<that conversation>.<turn id>`, never `$.session.id()` read at claim time, which right after a move back to A may still answer B; so it meets the coordinator's `<A>.<turn>` claim (its 0.9.3 fix round keys it the same way). A stop recorded without one (by 0.4.0, the plugin reloaded since) claims nothing and resumes nothing: "no resume: the conversation the interrupted turn ran in isn't known, so the resume can't be claimed".
- **self-reload 0.1.3: a reload queued before a /clear or /resume** (Low). At that SessionStart, while a reload this module armed waits, its resume is dropped (from the module's copy, and from `$.state` while the record is still there), and a toast and a note to the model say so: the reload still runs, but the resume was for the conversation left.
- **Shared code.** New: `shared/hooks/start-folder.ts` (`Copies: self-restart, self-switch`), the transcript check (`holdsTranscript`, `transcriptFolder`), on the shared machine code's `projectName` and `sameProject`. `shared/hooks/machine.ts` is unchanged. `shared/tests/update-check.test.ts` takes the machine variables a fixture's optional `ENV` names, beneath each test's own: self-restart's call now plans the launch at once, so it reads Windows'. ## 2026-11-01: the plugins say when they're out of date

Every plugin gets the same update check. Nothing else in them changed.

- When the main session calls one of a plugin's tools, and its last check is 30 minutes old or there hasn't been one, the plugin fetches its own `plugin.json` from the repository's `main` branch: a plain GET of a public file on raw.githubusercontent.com. The plugin adds no headers, query or body, and nothing about the person, the session or the machine; GitHub sees what it sees of any web request (the address, the time, the headers Claude Code sends on its own). It compares the `version` there with the installed one, number by number. The check's time and answer are kept in the plugin's own store, so a reload or another session on the machine uses that answer for the rest of the 30 minutes. Sessions that come due at the same moment each make their one request.
- The tool call never waits on the check. A failure is silence: offline, refused by policy, a 404, a rate limit, no answer within 5 seconds, bad JSON, or a version that isn't three plain numbers.
- When a newer version is out, a toast tells the person, and one of the session's next tool results ends with a fixed line: the plugin's name, the installed and the published versions, and the update steps for the person to run (`claude plugin marketplace update`, `claude plugin update`, then `/reload-plugins` or a new session), closing with "Don't run these yourself unless the person asks." Nothing else from the fetched file reaches the session. A session is told of each check once, and at most once every 30 minutes, kept across reloads, rather than on every call: these tools are called again and again in a long session, and the same line on every call would cost context and get tuned out. The toast follows the same rule.
