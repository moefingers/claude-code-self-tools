# self-update

Keeps the plugins this machine already has from the marketplaces you name current, with Claude Code's own `claude plugin` commands, and reloads each session behind an update at its next idle moment. Part of [claude-code-self-tools](../../README.md).

It is **off until you name a marketplace**. With its `autoUpdate` setting empty, the default, it makes no look, takes no lock, reads or writes no state file or install record, runs no command and reloads no session; an update stays a `claude plugin update` someone runs. Its one tool, `update_status`, still answers (it says self-update is off), and the update check every self tool has rides on it. Windows only in this release.

## Turn it on

Set `autoUpdate` to the marketplaces to keep current, comma-separated. In `/config`, or from your shell:

```
echo '{"autoUpdate":"claude-code-self-tools, example-marketplace"}' | claude plugin configure self-update@claude-code-self-tools --values-stdin
```

That saves it in settings.json as `"pluginConfigs": { "self-update@claude-code-self-tools": { "options": { "autoUpdate": "claude-code-self-tools, example-marketplace" } } }`. A session reads it when it loads the plugin: at its next start, or at a `/reload-plugins` that loads the plugin again (one that finds the plugin's code unchanged may leave it as it was, so a new start is the sure way). Empty it, or remove it, to turn it off. Naming `claude-code-self-tools` keeps self-update itself current too.

- **A name** is letters, digits, dots, dashes and underscores, a letter or a digit first, 64 characters at most, matched exactly (capitals included); 16 names at most. A value with any entry of another shape turns the whole feature off, the entries that fit too, and the session says why in its transcript, once.
- **A name no installed plugin comes from** (a misspelt one, say) does nothing, and the session whose look finds it says so in its transcript, once.
- **Whom you trust by naming a marketplace.** Whoever can publish to it, and more: a marketplace's entry can point a plugin at another repository or package, so the trust reaches whoever can publish each listed plugin's own source. And self-update follows whatever the marketplace's name points to on this machine now: a marketplace added again under the same name from a fork is followed to the fork. What they publish runs here with no review in between. Name only marketplaces whose code, and whose plugins' sources, you trust as they land.

`reloadAfterUpdate` (`on`, the default, or `off`) says whether a session behind an update reloads itself. Off, self-update only installs, and a session loads what it installed at its next start or `/reload-plugins`.

## What it does

- **When it looks.** At a session's start and at each main-loop turn's end, in a session a person is at (`claude -p` and SDK hosts don't look, and a subagent's turn end is no moment for a look); never from a timer of its own. A look is made only when the machine's last one is a whole interval old: 5 minutes while looks reach every named marketplace. Its time is in one file per plugins folder, beside the lock (`%LOCALAPPDATA%\claude-self-tools\auto-update\<key>.self-update.json`, `<key>` standing for Claude Code's plugins folder, since each plugins folder has its own install records), so ten sessions make one look per interval, not ten. A look under way writes that time before its first command and after each, so it reads as fresh for as long as it runs. A state file that is there but can't be read now (another program holds it) means no look now, and nothing written over it.
- **The lock.** The look takes a lock first (`…\auto-update\<key>.lock`), with the two scripts self-remote-control's Remote Control lock uses, byte for byte: the file made exclusively. A lock over 90 s old is taken over by the next taker, whether its holder is alive or not, so before each command a lock more than 5 s old is given back and taken again with a new time. A command never starts but under a lock at most 5 s old, and one command (with the plugin's backstop, 80 s at the most) ends before that lock is 90 s old. A look whose lock was taken over, or that can't take it again, stops at once, runs nothing more, and says so in the debug log; what its commands installed until then is still recorded.
- **What it runs.** Claude Code's own commands, their words fixed in one script: for each named marketplace that has a plugin installed here, `claude plugin marketplace update <marketplace>`; then, for every install record of it, `claude plugin update <plugin>@<marketplace> --scope <scope>`: the user's scope from the home folder, a project's or a local one from that record's own folder (one whose path starts with a drive letter, never a network path written as such, though a mapped drive or a junction can still lead to another machine; skipped while the folder is gone). What the marketplace has is installed at the next look, with no settling delay. The names that reach a command are checked to the name's shape twice, in the plugin and in the script.
- **Which `claude`.** `%USERPROFILE%\.local\bin\claude.exe` when it is there, wherever the command runs from; else the first `claude` on `PATH` that Windows can start (an npm install's `claude.cmd` too), never one the folder the command runs from could supply. For a project's or a local scope (run from that project's folder, a repository), that is any `claude` on `PATH` anywhere under the folder, however `PATH` names it (a relative `node_modules\.bin`, say), compared without regard to case. For the steps run from the home folder it is only one directly in it: an npm install's `claude.cmd` lives under the home folder, and is the one to run. When the only `claude` found on `PATH` sits inside, that one step fails, saying so, and nothing is run for it. The command gets `NoDefaultCurrentDirectoryInExePath=1`, so `cmd.exe` never looks in that folder for a program a `claude.cmd` names bare, `node` say.
- **A command never outlives its look.** The script starts the command as a child of its own. Its 55 s count from the script's own first line, so a cold PowerShell or a slow search for `claude` comes out of them: the command gets what is left, and with less than 5 s left it is never started. One that hasn't ended when the 55 s are up is ended with every process it started (Windows' own `taskkill /T /F`, the one other program self-update runs: claude, and the git or node under it), the script says so, and the look counts it as a failure and leaves that marketplace's other steps for the next look. The plugin's own timeout on the script (75 s, given up on 5 s later) is only the backstop.
- **What it never does.** Add a marketplace; install a plugin that has no install record; touch a marketplace the setting doesn't name (a named one with nothing installed here gets no command at all); name a version (so it never asks for an older one: `claude plugin update` alone picks it, from what the marketplace lists); pass `--force`; update a managed install. It reads Claude Code's install records (`installed_plugins.json`: names, scopes, folders, versions) before and after, whether a record's project folder is there, its own state file, this conversation's pending marker (below), and of each command its exit code and its last line; nothing else in Claude Code's folders is opened.
- **What it says.** One transcript line and one toast per install, a record that names another version or folder after the commands than before: `self-update: updated self-wake 0.4.0 to 0.4.1 from claude-code-self-tools; sessions reload at their next idle moment` (with `reloadAfterUpdate` off it ends `reloadAfterUpdate is off, so a session loads it at its next start or /reload-plugins`). Nothing when nothing changed. What leaves the machine: what the commands themselves fetch, and the update check's GET of this plugin's published `plugin.json` when `update_status` is called (below).

## Sessions pick an update up

A look that installed something leaves the time in its state file. A session whose plugins were loaded before that time is behind: one `/reload-plugins` loads what was installed. With `reloadAfterUpdate` on, it runs that reload itself:

- **Only at idle.** At a main-loop turn's end, or at the end of the session's own look, a beat after it, and only while nothing holds it, all read again right before it runs: no turn running; nothing typed in the prompt box (the read says only whether a draft stands; nothing of it is kept or logged); no subagent at work (any status but `idle`, `completed`, `failed` or `killed`); no look of this session's under way; no reload of this plugin's still out; and none in the last 15 minutes. Held, it waits for the next turn's end; it never interrupts a turn, and Claude Code runs a plugin's command only once the session is idle anyway. As it runs, the transcript and a toast say `self-update: running /reload-plugins: a plugin was updated on this machine after this session loaded its plugins.`
- **A reload that ran counts, whoever ran it.** Claude Code reloads only the plugins that changed, so self-update's own code may run on after a reload that took. A `/reload-plugins` that reloaded, self-update's own, a person's or another plugin's, moves the session's load time to the moment it ran, so a session that reloaded is behind no more.
- **Never a loop.** A try counts right before `/reload-plugins` runs, kept in the plugin's session state by the install's time. One that Claude Code skipped (it asks for `/reload-plugins --force`, when the reload would change which MCP tools are loaded) or that didn't run is tried once more, 15 minutes on at the soonest, then never again for that install, and the person reads one line in the transcript, once: `self-update: a plugin was updated on this machine after this session loaded its plugins, and two tries at /reload-plugins didn't reload them (skipped, or not run), so it tries no more for that update; /reload-plugins --force, a restart of this session, or a new one loads it.` Nothing is added to the conversation for it. A later install starts its own two tries. Never `/reload-plugins --force`: forcing a held reload re-reads the whole conversation without the prompt cache, which is the person's to choose.
- **This plugin's reload and a look never overlap.** A reload replaces the plugin's code, the look's among it. So the reload waits while this session's look is under way, and the look's end asks for it again; and no look starts while a reload of this plugin's is out. A `/reload-plugins` a person or another plugin runs during a look is not held (below).
- **Every session reloads for any install**, one in another project too (a local scope's update of project A reloads a session in project B, once), and a session that started while the look ran reloads once more than it needed.

## An exit or a restart pending

self-exit and self-restart write a marker for the conversation while an exit or a restart is queued or armed (`%LOCALAPPDATA%\claude-self-tools\pending\<conversation>.json`), and check, right before their command, that nothing runs under the session; a look's PowerShell, claude or git would make them refuse. So while this conversation's marker says one is pending (at most 15 minutes old), no look starts (the next turn's end, or the next session, looks), and a look under way stops before its next command. self-update only reads the marker. self-switch writes none, so a switch is not seen: a look that starts at the turn's end where a switch was queued can make that switch refuse, saying a background job runs; calling it again once the look is over works.

## Failures

- **A command that fails** (its exit code, its time run out, or one that couldn't be started) is recorded and tried again at the next look, never sooner. A marketplace whose refresh failed has its plugins left for that next look too.
- **The wait to the next look stretches only when a look couldn't reach a named marketplace**: its refresh (`claude plugin marketplace update`) failed, ran out of time or couldn't be started. Each such look in a row doubles it: 10 minutes after one, then 20, then 40, then an hour, until a look reaches every named marketplace and the 5 minutes come back. The count is in the state file, so it holds for the whole machine: a machine whose marketplace login lapsed tries 24 times a day, not 288.
- **A plugin's own update failing never stretches it** (a retired plugin's record, a half-deleted worktree's local one): it is recorded and tried again at every look, five minutes apart, and the other plugins go on being updated at that pace.
- **Three looks in a row with a failure get one toast**, with the command and its last line: `self-update: failed 3 looks in a row; it goes on trying at every look; the last: claude plugin update … : …`, or, when a marketplace wasn't reached three looks in a row, `self-update: couldn't reach a marketplace 3 looks in a row; it goes on trying, less often (once an hour at the least), until a look reaches them all; the last: claude plugin marketplace update … : …`.
- **A command's last line is masked before it is kept, logged or shown, then cut to 200 characters**, so a cut never leaves part of a secret: a URL's user and password; the word after Bearer or Basic, and a cookie header's value; a value given by a name that says secret, of any length and in any of the usual forms (`token=…`, `password: …`, `"secret": "…"`, `Authorization: token …`, `X-Api-Key: …`); tokens of their issuers' shapes from 8 characters past the prefix (GitHub, GitLab, Slack, `sk-`, AWS key ids, Google API keys, JSON web tokens); and runs that read as random (letters and digits of mixed case, base64 with `+` and `/`). A secret's name in prose takes its next word with it (`invalid token: ‹secret›`). `update_status` quotes the line as data. self-secret's redaction scrubs a value it knows, so it doesn't fit here, and this repository has no other masker by shape.
- **No `claude` that Windows can start**: the session says so once in its transcript, and runs nothing more.

## Beside another plugin that keeps plugins current

Another plugin can keep plugins current the same way, with its own setting. On a machine with both, they take the same lock file (`…\auto-update\<key>.lock`) with the same two scripts, and each keeps a state file of its own beside it, which the other never reads or writes. self-update never runs a command without holding a fresh lock, renewed before each command. An updater that holds the lock longer than 90 s without renewing it can be taken over, and then both run commands at once, so the two stay apart only while both renew the lock this way. With both set for the same marketplace, each looks on its own interval, and a look that finds nothing newer changes nothing. Each one's sessions reload for the installs its own looks made.

## Where it doesn't run

- **Windows only**: the lock's scripts and the command's script are Windows PowerShell's. Elsewhere, or where the machine's folders can't be placed, it does nothing and says so once in the debug log.
- **Headless sessions** (`claude -p`, SDK hosts) don't look and don't reload.
- **While a look runs**, its PowerShell (and the claude and git under it) are processes of this session: self-switch, or an exit or a restart asked for while the look was already under way, checking the session in those seconds, can see a running shell or a git operation and refuse, naming a background job with no task to stop. It passes once the look ends; each command is bounded at 80 s.

## Known limits

- When a command runs out of time, `taskkill /T` follows parent process ids: a process the command started whose own parent has already ended is not in that tree and is left running, and in the rare case that Windows has given one of the tree's ids to an unrelated process that still names it as its parent, that one is ended too.
- The plugin's backstop gives a script 20 s more than the command's own 55 s, for Windows PowerShell's start and the tree's end. A machine so loaded that PowerShell takes longer than about 10 s to start can see the backstop end PowerShell before the script ends its tree, and the claude and git under it are then left running.
- A plugin's update that runs out of its time at every look ends that marketplace's remaining updates at every look, and the order is fixed, so the plugins after it in that marketplace wait while it hangs.
- On a machine with only an npm `claude`, a local or project install recorded at the home folder (or a folder above it) never updates: its step finds the only `claude` under the folder it runs from. `%USERPROFILE%\.local\bin\claude.exe`, when it is there, is run even for a project under the home folder, and even when the session itself runs another `claude` (a native install left behind after a move to npm, say).
- A local or project step runs `claude` in that project's folder, in the background, so whatever settings that project's `.claude` folder holds that `claude plugin update` honours apply to it, unseen. Which of them it honours was not determined.
- A `/reload-plugins` that a person or another plugin runs in the middle of a look is not held: that look's lock goes stale in 90 s, and what it installed is recorded by no one, so other sessions load it at their next start or reload.
- With one plugin's update failing for good, the toast for a marketplace that couldn't be reached three looks in a row comes again each time that happens after a look that reached it.

## Tool

`update_status` (Claude sees `mcp__self-update__update_status`): what self-update does on this machine and in this session. The marketplaces `autoUpdate` names (or why it is off), when the machine last looked and when the next look comes, the failures in a row and the last one (quoted as data), the looks in a row that couldn't reach a marketplace, when a look last installed something, and whether this session is behind it and reloads at its next idle moment. Read-only: it runs no command and changes nothing; with the setting empty it reads none of self-update's files. A subagent is refused: the status is the main session's.

## Update check

When Claude calls this plugin's tool, and the last check is 30 minutes old or there hasn't been one, the plugin checks whether a newer version is published, as every self tool does. It fetches this plugin's `plugin.json` from the `main` branch of the repository its installed `plugin.json` names, [`plugins/self-update/.claude-plugin/plugin.json`](https://raw.githubusercontent.com/moefingers/claude-code-self-tools/main/plugins/self-update/.claude-plugin/plugin.json), and compares its `version` with the installed one: a plain GET of a public file, at most every 30 minutes, never holding up the tool. When a newer version is out, a toast tells you, and one of Claude's next answers from the tool ends with the update steps for you to run. Turn it off with the plugin's `updateCheck` setting (`off`); it is also off while `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is set. With `autoUpdate` naming `claude-code-self-tools`, self-update installs its own newer version at the next look.

## Tests

`tests/self-update.test.ts` runs the plugin in the engine's test kit, with the commands and the lock's scripts stood in (no real `claude`, PowerShell or network); `tests/update-logic.test.ts` tests the pure side; `scripts/self-update.test.mjs` holds the lock's scripts equal to self-remote-control's and the PowerShell call and the pending marker's reading equal to the shared machine code's, and, on Windows only, runs the command's script by a real Windows PowerShell against a stand-in `claude.cmd`. No test runs a real `claude plugin update`.

```
/plugin marketplace add moefingers/claude-code-self-tools
/plugin install self-update@claude-code-self-tools
```
