# self-restart

Lets a session restart itself on Windows. Once the current turn ends, it opens a new terminal window in the folder the session started in and exits; the new window resumes the same conversation (`claude --resume <id>`) once the old process has gone, and can start its first turn with a message the session left. When Claude Code was started through the [claude wrapper](../../tools/claude-wrapper/claude-wrapper.ps1) (a `claude` function in your PowerShell profile), it resumes in the same tab instead; in a pane set up as a [slot](../self-switch#slots-keep-your-panes), it resumes there; neither opens a new window. It's useful after an account switch, a setting that takes effect at startup, or a plugin that won't reload. Part of [claude-code-self-tools](../../README.md).

## Tool

`restart_after_turn` (Claude sees `mcp__self-restart__restart_after_turn`):

- `reason` (required): why the session restarts. It is recorded in the transcript.
- `resume` (optional): the message that starts the session's first turn after the restart: what to check or do next.

## How it behaves

- **Only at a finished break.** A session calls it once a piece of work is finished, never mid-merge, mid-push or mid-task: the same rule as compacting with [self-compact](../self-compact). The tool's description says so.
- **The restart waits for the turn to end.** The call queues it, and it starts once the turn ends with Claude's answer.
- **One new window, by a fixed path.** The plugin runs Windows PowerShell by its known path under the Windows folder (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe`), with one fixed script whose only variables are the session's id, which must be a UUID, its start folder, the claim and the times below, each checked before it is used, on PowerShell's standard input (the command line is a fixed few hundred characters; the new window's carries its script compressed). Nothing Claude passes reaches that script or its command line.
  - The script finds the session's own `claude.exe` above it.
  - It opens a new console window with `Start-Process`. When Windows Terminal is your default terminal, the window opens there.
  - That window waits for the old `claude.exe` to exit, then runs [`claude-launch.ps1`](../self-switch/slot/claude-launch.ps1)` -Resume <id>`, in the folder the session started in (where `--resume` finds it, even after the session moved into a worktree or another folder). The script runs only from `%LOCALAPPDATA%\claude-self-tools\claude-launch-<first 8 hex digits of its SHA-256>.ps1`, and only with the SHA-256 this version ships (`LAUNCH_SCRIPT_SHA256`), under `-ExecutionPolicy Bypass` for that window alone (the hash is the check): the launch puts its own copy there first when the file is missing or has another hash, and when it can't, the restart is refused, saying why, and nothing exits. A run of it that stops on an error is caught, and the window says how to resume by hand. `claude-launch.ps1` runs `%USERPROFILE%\.local\bin\claude.exe` when it is there, else `claude` from your PATH.
  - The script is the shared launcher, `launch()`, which self-switch uses too: the plugins share one module of machine code (`hooks/machine.ts`, a copy of `shared/hooks/machine.ts`).
  - **A deadline.** The launch is placed within 20 seconds of the call that plans it, or not at all; one found placed late is taken back (its ticket or record overwritten as withdrawn, its claim released), and a take-back that couldn't be confirmed is tried again 3 seconds later. The restart then says so, and nothing exits.
- **The session's own process.** Walking up from the launcher, a parent counts only while it is older than its child. A process that later took a gone parent's id is never mistaken for the session.
- **A resume that fails says so.** If Claude Code ends with an error, or within seconds of starting, the window shows `claude --resume <id>` and waits for Enter instead of closing on the message. A resumed session that ran and ended closes its window as a terminal does.
- **A top-level session, not a nested one.** The window inherits the old session's environment, which carries the markers Claude Code sets in the processes it starts. One of them, `CLAUDE_CODE_CHILD_SESSION`, would make the resumed session count as nested, and a nested session saves no transcript. So `claude-launch.ps1` clears a fixed list of those markers right before it runs `claude --resume` (the list and its sources are in `hooks/machine.ts`, `SESSION_MARKERS` and `LAUNCH_ENV_CLEAR`), and `NO_COLOR`, which Claude Code sets in its tool shells (the resumed session would draw no colour), and `PSExecutionPolicyPreference` and `CLAUDE_PANE_TOKEN` (`LAUNCH_ENV_DROP`). Then it sets `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1`, so a marker a later Claude Code adds can never turn transcripts off. It is inherited by everything the resumed session starts, so a `claude` run nested in it (from its Bash or PowerShell) saves a transcript too, and is listed by `--resume` and picked by `--continue` in that folder; Claude Code otherwise leaves nested runs out. `WT_SESSION` and `WT_PROFILE_ID` are left as the new window has them: Claude Code reads `WT_SESSION` to draw its Unicode prompt and its links. It sets `CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1` too (`LAUNCH_ENV_SET`): the page file carries the load, rather than background shells being reaped. Your other variables are left as they are. The [root README](../../README.md#the-launch-environment) has the list.
- **Never two copies of one session.** If the old process is still running after 10 minutes, the window says so and resumes nothing, because two copies would both write to one session. You can then run `claude --resume <id>` yourself.
- **A last look before it resumes.** After the wait, right before `claude --resume`, the window reads Claude Code's session registry and the process table again, and resumes nothing if another process holds the conversation by then. A running `claude.exe` whose registry file names the conversation holds it whatever its `procStart`, and so does a process whose command line names it (`--resume`), unless it is a `claude.exe` whose own current registry entry names another conversation (it was started that way and switched in place since). A process that has exited by then is passed over: it holds nothing (the old session, started as `claude --resume <id>` itself, names the conversation on its command line).
- **The claim lock.** The launcher takes `%LOCALAPPDATA%\claude-self-tools\claims\<id>.lock`, created only if it isn't there, so a [switch](../self-switch) moving the same conversation can't resume it too; the window resumes only while the lock still names it, and the resumed session's copy of the plugin releases it. A lock whose creator has gone counts no more after 15 minutes. If another switch or restart holds it, nothing opens and nothing exits.
- **No permission flag.** The window runs `claude-launch.ps1 -Resume <id>`, which runs `claude --resume <id>` and nothing more: the resumed session starts in the mode a new session would.
- **In the same tab, through the claude wrapper, tried first.** With [`tools/claude-wrapper/claude-wrapper.ps1`](../../tools/claude-wrapper/claude-wrapper.ps1) in your PowerShell profile, typing `claude` gives the session a token, `CLAUDE_PANE_TOKEN`, and a pane file, `%LOCALAPPDATA%\claude-self-tools\panes\<token>.json`, naming the PowerShell that runs it by its process id and start time. When that PowerShell is this `claude.exe`'s own parent (on the probe the safe point was judged on: the same process id, and a start within 1 ms), and the pane file is of version 3 (the wrapper that checks the claim and takes the last look in every config folder the ticket names), or of version 2 when the restart reads one config folder alone (an older one, or a version 2 one under more than one config folder, gets a new window, and says why), one fixed script takes the claim lock for one launch and leaves the wrapper a ticket, `panes\<token>.next.json` (`{ "v": 1, "token", "resume", "by", "dir", "at", "configDirs" }`: this session's id, the claim, the folder it started in, now, and the config folders it reads), written whole under another name and moved into place; no window opens. Once the session exits, the wrapper deletes the ticket, checks it (this tab's token, a session id and a launch's claim, at most 120 seconds old, an existing folder whose project holds the session's transcript, its config folders absolute folders, the claim lock on the session still naming the ticket's claim), takes the window's last look right before claude runs (no running Claude Code holds the session, from the registry of its own config folder and of each the ticket names, and every command line, read again), and runs `claude --resume <id>` in that folder, in the same tab, with the markers and `NO_COLOR` cleared and `CLAUDE_CODE_FORCE_SESSION_PERSISTENCE=1`, as the window does. A `claude` started under another one (from its Bash or PowerShell) inherits the token, but its parent is that shell: it gets a new window. A session with a token whose tab can't be used (no pane file, a pane file of version 1, another parent, another start time) gets a new window too, and the log and the row the restarted session reads say why. If the exit is stopped after the ticket was written, the tab resumes the session if it exits within 2 minutes, as a slot does; the restart's record keeps its claim (not its first prompt), so the session resumed there releases it, whichever of the tab, the slot or the window resumes it. With no `LOCALAPPDATA` (an SSH or remoting shell), the wrapper just runs claude, with no token. Without the wrapper, nothing changes.
- **In a slot, no new window.** When the session's `claude.exe` runs in a pane set up as a slot (a Windows Terminal pane running self-switch's `claude-slot.ps1`, its SHA-256 the one the plugin ships), the launcher leaves the slot a record instead of opening a window; once the session exits, the slot resumes it in the same pane, after the same checks. A slot it passes over (its script can't be hashed, is over 64 KB, or has another hash; the pane runs `claude-slot.ps1` some other way than the runner it recognises; or the start folder isn't one the runner takes) gets a new window, and the restart says why, in the row the restarted session reads, a toast and the log: for example *slot hash unreadable: …*. The hash is computed with .NET, so a Windows Terminal tab whose module path lists PowerShell 7's folders first still finds its slot.
- **The first prompt never goes on a command line.** `resume` waits in the plugin's own store under the session's id. The copy of this plugin in the resumed session sends it once, when that session starts. One older than 15 minutes is dropped.
- **Remote Control.** With "Enable Remote Control for all sessions" on, the resumed session connects again, under the same conversation. A copy started while the old one was still connected would leave Remote Control off, which is one more reason the window waits.
- **Everything else this process runs ends with it:** wake-ups and background tasks.
- **Nothing that would make the exit ask.** The restart's `/exit` must not meet a confirmation dialog, so the plugin runs [self-exit](../self-exit)'s pre-check (`exitBlockers`, in the shared machine code) and refuses while anything stands, naming each with how to stop it: a session cron (read with the built-in `CronList` tool, only after the permission check says `allow`, so never a dialog: *delete it with CronDelete (id …)*), a background Bash, PowerShell or Monitor job, a build or a heavy-slot run under the session (*stop it with TaskStop …*), a subagent that hasn't ended (an idle teammate, or a status the plugin doesn't know, with how to clear it: TaskStop, or exit by hand). Anything it can't read refuses too, saying *can't tell* and why. It checks at the call, so nothing is queued while anything stands, and again when the restart is armed. Each blocker was seen, alone, to make a queued `/exit` stop at its *Background work is running* dialog; the live checks ran in bypassPermissions mode, so `CronList`'s permission in the default mode is untested (where it isn't `allow`, the restart is refused, never queued into a dialog). Where the launch can't be planned (off Windows, an id `claude --resume` doesn't take), the call reads crons and subagents only, and the restart is refused when armed, saying why.
- **Not while subagents are running.** Their work would end with the process. Besides the pre-check, a subagent started by the time the restart would run cancels it, and one started while the window opens stops the exit.
- **Only at a safe point.** Right before the launch, with the pre-check, the plugin runs the same safe point as [self-switch](../self-switch), on the same probe of the processes under this session's `claude.exe`, and git's state where it started and works. It refuses while anything still runs under it (a background Bash, PowerShell or Monitor job, `git`, a build, test or lint, a dev server or Playwright, a heavy-slot job) or a git operation is in flight in any worktree of the repo (`index.lock`, a rebase, a merge, a cherry-pick, a revert, a bisect). Anything it can't read holds the restart and says what. Stdio MCP servers don't count.
- **The pending marker.** While the restart is queued or armed, the plugin keeps `%LOCALAPPDATA%\claude-self-tools\pending\<conversation>.json` as `{ "v": 1, "kind": "restart", "at": <milliseconds since the epoch> }`, and overwrites it with `{ "v": 1, "done": true }` right before the exit runs, or when the restart is cancelled or refused. The [coordinator](https://github.com/moefingers/agent-coordinator-3000) holds its deliveries while it says pending and is at most 15 minutes old, so that none starts a turn that cancels the restart; they reach the resumed session. [self-exit](../self-exit#how-it-behaves) has the contract in full.
- **No restart loop.** A session whose restart opened its window less than 2 minutes ago is refused another, at the call and again right before the launch.
- **Windows only, in a terminal.** Elsewhere nothing runs, and Claude is told on its next turn. A session in an app, an SDK host or a `-p` run is refused at the call.
- **It says when a step didn't work.** If the window doesn't open, nothing exits. If the exit doesn't run, the window keeps waiting for you to exit (`/exit`), up to 10 minutes.
- **An interrupted turn cancels it**, with a notice.
- **A cancel is never lost.** When a new turn (a message, a watch event) takes a queued restart back, that turn reads a row: *self-restart: your queued restart was cancelled because a new turn started; queue it again at the next finished break.* Cancels are counted while they come in a row; from the third, the row adds that the session is busy: queue it again when it's idle, or ask the merger or the owner. A restart whose run begins ends the count.
- **Subagents can't use it.** A subagent is told to finish its piece and return its result.

To end the session without a restart, see [self-exit](../self-exit). To pick up a plugin change without a restart, see [self-reload](../self-reload).

## Update check

When Claude calls this plugin's tool, and the last check is 30 minutes old or there hasn't been one, the plugin checks whether a newer version is published. It fetches this plugin's `plugin.json` from the `main` branch of the repository its installed `plugin.json` names, [`plugins/self-restart/.claude-plugin/plugin.json`](https://raw.githubusercontent.com/moefingers/claude-code-self-tools/main/plugins/self-restart/.claude-plugin/plugin.json), and compares its `version` with the installed one.

- **A plain GET of a public file.** The plugin adds no headers, query or body, and sends nothing about you, the session or the machine. GitHub sees the request as it sees any web request: the address it comes from, the time, and the headers Claude Code sends on its own.
- **At most every 30 minutes.** The check's time and answer are kept in the plugin's own store, so a reload, or another session on this machine, uses that answer until it is 30 minutes old. Sessions that come due at the same moment each make their one request.
- **It never holds up the tool.** The check runs beside the call, which never waits on it. Offline, refused by policy, a 404, a rate limit, no answer within 5 seconds, or anything but a plain version such as `0.2.0` all mean no notice.
- **When a newer version is out**, a toast tells you, and the result of one of Claude's next calls ends with a line like this:

  > self-restart 0.1.2 is out of date (0.2.0 is published). To update, the person runs: claude plugin marketplace update claude-code-self-tools, then claude plugin update self-restart@claude-code-self-tools, then /reload-plugins in each open session (a new session loads the update on its own). Don't run these yourself unless the person asks.

  The line is fixed text. Only the two version numbers vary, and each must be three plain numbers. Nothing else from the fetched file reaches Claude. A session is told of each check once, and at most once every 30 minutes, not on every call, and the toast follows the same rule. A call carries only what an earlier check found: the call that starts a check doesn't wait for its answer.
- **Turn it off** with the plugin's `updateCheck` setting: `off` never checks. Set it in `/config`, or from your shell:

  ```
  echo '{"updateCheck":"off"}' | claude plugin configure self-restart@claude-code-self-tools --values-stdin
  ```

  which saves it in settings.json as `"pluginConfigs": { "self-restart@claude-code-self-tools": { "options": { "updateCheck": "off" } } }`. Nothing is checked while `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` is set, to any value, or for a subagent's call.
